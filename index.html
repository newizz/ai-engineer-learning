🏭 Predictive Maintenance Application

Pump Vibration Anomaly — กรอบปัญหาแบบ Applied AI

โรงงานมีปั๊ม 200 ตัว — เคยพังกะทันหัน 12 ครั้ง/ปี ค่าเสียหายครั้งละ ~5 ล้านบาท. หัวหน้าบอก "ทำ AI ป้องกันได้ไหม?"

คำถาม Applied AI Engineer ต้องถามก่อน code:

  • มี sensor อะไรบ้าง? sample rate? ส่งมายังไง?
  • มีข้อมูล "พัง" ในอดีตกี่ครั้ง? (label มีไหม?)
  • ต้อง alert ก่อนพังกี่ชั่วโมง/วัน? (=Lead time)
  • False alarm ต้นทุนเท่าไหร่ vs miss detection?
  • ต้องอธิบายเหตุผลได้ไหม? (explainability)

Process: Applied AI Project ทุกตัว ทำตามนี้

  1. Business Understandingเข้าใจปัญหาและ KPI ของธุรกิจก่อน — "ลด downtime 30%" ดีกว่า "build AI model"
  2. Data Auditมีข้อมูลอะไร? คุณภาพยังไง? เข้าถึงได้แค่ไหน? (ขั้นนี้กิน 40% ของ project จริง)
  3. Problem Framingแปลปัญหาเป็น AI task: classification? regression? anomaly detection? generation?
  4. Choose Tool, Not Algorithmเริ่มจากที่ง่ายสุด — rule-based → simple ML → LLM. ไม่ใช่กระโดดไป Transformer
  5. MVP & Shipสร้างเวอร์ชันใช้งานได้ใน 2-4 สัปดาห์ deploy ให้ user จริงเล่น
  6. Measure & Iterateเก็บ metric, feedback, drift — ปรับทุก sprint

Common Pitfalls ของ Beginner

  • Tech-First Trap — เลือก tool ก่อนเข้าใจปัญหา ("ใช้ LLM ดีไหม?" → ก่อนถามว่าปัญหาคืออะไร)
  • Accuracy Obsession — โหมเอา accuracy สูงโดยไม่สนว่าใช้งานได้จริงไหม
  • Scope Creep — รับงานทุกอย่าง พยายามแก้ทุก use case
  • Over-Engineering — สร้าง pipeline 10 component ทั้งที่ rule-based 50 บรรทัดก็พอ
  • No Success Metric — ไม่กำหนดล่วงหน้าว่า "เสร็จ" คืออะไร
  • Demo ≠ Production — โชว์ demo ดี แต่ production พังเพราะ edge case

วิธีคิดและแก้ปัญหาแบบ Senior

  • เริ่มจาก "Why" ไม่ใช่ "How" — ปัญหาธุรกิจคืออะไร? วัดผลยังไง? ก่อนแตะ tech
  • Define Done — เขียน success criteria ก่อนเริ่ม (e.g., "ลด unplanned downtime 25% ใน 6 เดือน")
  • Choose Simplest Solution That Works — Occam's Razor: rule-based → ML → LLM ตามลำดับ
  • Build for Failure — ทุกระบบจะพัง ออกแบบให้พังแบบสง่างาม (graceful degradation)
  • Ship Early, Ship Often — 2-week MVP ดีกว่า 6-month perfect
  • Talk to Users — หา 1-2 user จริง ใช้งานทุกสัปดาห์ ฟัง feedback

Module 1 — LLM Foundations

เข้าใจ LLM แบบ engineer — ไม่ต้องลึกถึง matrix แต่ต้องรู้ว่ามันคิดเงิน คิดเวลา คิดบริบทยังไง

💡 Mental Model: LLM = นักเรียนความจำดี ที่อ่านหนังสือมาเยอะ — แต่ จำเฉพาะตอนสอบ (context window) และ ไม่อัปเดตหลังเรียนจบ (knowledge cutoff)

4 ศัพท์ที่ต้องรู้ ก่อนคุยกับ LLM ได้

1. Token = หน่วยย่อยที่ LLM อ่าน/เขียน (≈ 1 token = 0.75 คำอังกฤษ / 1 ตัวอักษรไทย). สำคัญเพราะ คิดเงินตาม token

"Hello world"           → 2 tokens
"สวัสดี"                  → 6 tokens (ไทยกินเยอะกว่า!)
"def add(a, b):"        → 6 tokens

2. Context Window = "ความจำชั่วคราว" ของ LLM ในแต่ละครั้งที่คุย (เช่น GPT-4: 128k, Claude Sonnet: 200k, Gemini: 1M+)

3. Embedding = แปลงข้อความเป็นเวกเตอร์ตัวเลข เพื่อหา "ความหมายใกล้เคียง" — หัวใจของ RAG

4. Knowledge Cutoff = วันที่ความรู้ของโมเดลหยุด — ถามเรื่องหลังจากนั้นจะ แต่ง (hallucinate)

โรงงานมี free-text log ของช่างซ่อมบำรุง 50,000 รายการ — เขียนแบบไม่มาตรฐาน. ใช้ LLM (Workhorse tier) classify: fault type, severity, root cause → ใส่ DB → ใช้เป็น input ของ predictive model

Pipeline: Free-text log → LLM (extract structured) → SQL Database → Dashboard

เรียก LLM API ครั้งแรก: Steps

  1. เลือก provider + model tierเริ่มที่ Workhorse (Sonnet/4o) สำหรับงานทั่วไป
  2. ตั้ง API key + budget alertset spending limit ใน console ทันที (อย่าข้าม!)
  3. เขียน prompt + call APIส่ง message → รอ response → parse output
  4. Track tokens + latencylog input_tokens, output_tokens, elapsed_ms ทุก call
  5. Handle errorsretry, timeout, rate limit, content filter
  6. Stream outputใช้ streaming สำหรับ UX ที่ดี (ไม่ให้ user รอนาน)

โค้ดตัวอย่าง: Python + Anthropic SDK

import anthropic, os, time

client = anthropic.Anthropic(api_key=os.getenv("ANTHROPIC_API_KEY"))

start = time.time()
msg = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=512,                  # 🛡️ guard: จำกัด output
    messages=[
        {"role": "user", "content": "สรุป fault log นี้ใน 1 บรรทัด: ..."}
    ],
)
print(f"in={msg.usage.input_tokens}  out={msg.usage.output_tokens}")
print(f"latency={time.time()-start:.2f}s")
print(msg.content[0].text)

Issues ที่ Beginner เจอบ่อย

  • Hallucination — LLM แต่งคำตอบเมื่อไม่รู้ (โดยเฉพาะตัวเลข/วันที่)
  • Context Overflow — ใส่ข้อความยาวเกิน window → error หรือตัด context หาย
  • Latency Spike — บางครั้ง API ตอบ 30+ วิ → ผู้ใช้หนี
  • Cost Explosion — token blow-up จาก long context, retry loop, agent loop
  • Rate Limit — เรียกถี่เกิน → ถูก throttle → service พัง
  • Output Format Drift — ขอ JSON ได้บ้างไม่ได้บ้าง
  • Knowledge Cutoff — ตอบเรื่องปัจจุบันผิด

วิธีแก้แบบ Senior

  • Hallucination → ใช้ RAG (ป้อนข้อมูลจริง), เพิ่ม "ถ้าไม่รู้ให้บอก", ใช้ structured output
  • Context Overflow → chunk + retrieve top-K, summarize history, ใช้ model context ใหญ่กว่า
  • Latency → streaming, smaller model สำหรับ classification, parallel calls, cache
  • Cost → tier routing (Haiku ก่อน Opus), prompt caching, semantic cache, max_tokens guard
  • Rate Limit → exponential backoff, queue, multiple API keys, fallback model
  • Format Drift → JSON mode / Tool use / structured output / Pydantic schemas
  • Knowledge Cutoff → RAG + web search tool

Module 2 — Prompt Engineering

Prompt = Code — ต้องเขียนดี version ได้ test ได้ ไม่ใช่ "ลองพิมพ์ดู"

💡 Mental Model: Prompt = สเปคงานให้ junior dev ที่เก่งมาก แต่ขี้ลืม + พูดมากไป — ต้องบอกให้ชัด, ให้ตัวอย่าง, ระบุรูปแบบส่ง, จำกัดขอบเขต

Anatomy ของ Prompt ที่ดี

Prompt ที่ดีมี 6 ส่วน — เขียนตามลำดับนี้

  1. Role / Persona"คุณเป็นวิศวกรบำรุงรักษา 15 ปี..."
  2. Task"วิเคราะห์ fault log ต่อไปนี้และระบุสาเหตุ"
  3. Context / Backgroundข้อมูลพื้นฐาน, constraint, audience
  4. Examples (Few-shot)ตัวอย่าง input/output 2-3 ตัว — เพิ่ม accuracy 20-40%
  5. Output FormatJSON schema, markdown structure, ภาษา
  6. Guardrails"ถ้าไม่แน่ใจให้บอกว่า unknown", "อย่าแต่งตัวเลข"

เทคนิคเด็ด ที่ใช้บ่อย

Chain-of-Thought (CoT): เพิ่ม "คิดทีละขั้นก่อนตอบ" → accuracy เพิ่มในงาน reasoning 15-30%

Few-Shot Examples: ใส่ 2-5 ตัวอย่างก่อนคำถามจริง (ใส่ตัวอย่างยาก ๆ ด้วย)

Structured Output: บังคับ JSON / Pydantic schema → parse ง่าย, drift น้อย

Negative Constraints: "อย่า..." แทนที่จะ "ให้..." บางครั้งได้ผลดีกว่า

XML Tags (Claude): ใช้ <context>...</context> แยกส่วนชัดเจน

🏭 Predictive Maintenance Application

Fault Diagnosis Prompt — ตัวอย่างจริง

SYSTEM: คุณเป็น senior reliability engineer 15 ปี เชี่ยวชาญปั๊ม centrifugal
ตอบเป็น JSON เท่านั้น ตามรูปแบบ:
{"fault_type": str, "severity": "low|medium|high", "root_cause": str, "action": str, "confidence": 0-1}

ถ้าข้อมูลไม่พอ ให้ confidence < 0.5 และ fault_type = "insufficient_data"

EXAMPLES:
Input: "Pump P-101 vibration 8.5 mm/s, oil temp 85°C, runtime 4500hr"
Output: {"fault_type": "bearing_wear", "severity": "high", ...}

USER: {sensor_reading_here}

ทำไมดี: Role ชัด · Output structured · Few-shot · Guardrail (insufficient_data) · Confidence score

Process: เขียน Production Prompt ใน 6 Steps

  1. Define Task & Successเขียนเป็นภาษาคน: input อะไร, output อะไร, "ดี" คือยังไง
  2. Draft v1เขียน prompt แรก ทดสอบกับ 5-10 ตัวอย่าง
  3. Add Examplesเลือก few-shot ที่ครอบคลุม edge case
  4. Add Guardrailsใส่ "ถ้าไม่รู้...", "อย่า..." กัน hallucinate
  5. Test & Iterateมี eval set 30-50 ตัวอย่าง → วัด accuracy/format compliance
  6. Version Controlเก็บ prompt ใน git, tag version, A/B test

Common Prompt Issues

  • Prompt Injection — user แทรกคำสั่งเพื่อ override system
  • Instruction Drift — ใน conversation ยาว ๆ LLM ลืม system prompt
  • Format Breakage — ขอ JSON ได้บ้างไม่ได้บ้าง, parse fail
  • Verbosity — ตอบยาวไป, อธิบายไม่หยุด ทั้งที่ขอสั้น
  • Refusal — ปฏิเสธทำงาน เพราะคิดว่าผิด policy ทั้งที่ไม่ผิด
  • Inconsistency — input เดียวกัน ตอบไม่เหมือนกัน 2 รอบ
  • Language Drift — ขอภาษาไทย แต่บางครั้งตอบอังกฤษ

Resolutions แบบ Senior

  • Prompt Injection → ใส่ user content ใน <user_input> tag, validate output, sandbox tool calls, มี guardrail layer (เช่น Llama Guard)
  • Instruction Drift → ทวน instruction ทุก N turns, summarize history เป็น system message
  • Format Breakage → ใช้ structured output / JSON mode / tool-use, validate ด้วย Pydantic, retry on fail
  • Verbosity → "ตอบไม่เกิน 3 ประโยค", set max_tokens
  • Refusal → เพิ่ม context ทำไมต้องทำ, ใช้ system prompt อธิบาย legitimate use
  • Inconsistency → set temperature=0 สำหรับงาน deterministic, ใส่ seed
  • Language Drift → ระบุภาษาใน system prompt + few-shot ทั้งหมดเป็นภาษานั้น

Process: ออกแบบ Context Window

  1. Define Token Budgetเลือก model + ดู context window (Sonnet=200k, GPT-4o=128k, Haiku=200k) แล้วเหลือเผื่อ output 10-20%
  2. Allocate per Layerกระจาย token ระหว่าง 6 layers ตาม priority ของ use case
  3. Prioritize Positionวาง critical info ที่ ต้น (system) + ท้าย (ก่อน user) — กันโดน "lost in middle"
  4. Compress Historyทุก N turns สรุป conversation เป็น summary 200 tokens แทนเก็บทั้งหมด
  5. Re-rank Retrievedดึง top-20 จาก vector DB → re-rank → keep top-3 ที่ relevant ที่สุด
  6. Tool Pruningเฉพาะ agent: เลือก 3-5 tools ที่เกี่ยวข้องกับ query นี้ ไม่ใช่ส่ง 50 tools ทุกครั้ง
  7. Test Under Loadsimulate การใช้งานยาวเป็นชั่วโมง ดูว่า token ทะลุ window ไหม
  8. Monitor in Productionlog tokens_per_layer, alert เมื่อเกิน threshold

Issues จริงที่เกิดใน Production

  • Context Overflow — token รวมเกิน window → API error หรือ truncate ข้อมูลเงียบ ๆ
  • Lost in the Middle — ใส่ chunks 20 ตัวกลาง context → LLM ละเลยตัวกลาง
  • Memory Bloat — history สะสมจนกิน 60% ของ window → ที่เหลือไม่พอ
  • Few-Shot Pollution — examples มี style/topic ต่างจากงานจริง → output เพี้ยน
  • Tool Definition Spam — agent มี 30 tools → confused, เลือกผิด
  • Contradicting Information — system บอก A, retrieved บอก B → LLM งง
  • Format Collision — system ขอ JSON, retrieved chunk มี markdown → output mix
  • Prompt Injection via Retrieved Content — RAG ดึงเอกสารที่มี "Ignore previous instructions" มา → bot โดนยิง

Module 3 — RAG (Retrieval-Augmented Generation)

หัวใจของ Applied AI ในงานจริง 80%+ ของระบบ LLM ใน enterprise คือ RAG

💡 Mental Model: ให้ LLM อ่านสมุดโน้ตของคุณก่อนตอบ — แทนที่จะให้มันเดาจากความจำ (training data) RAG = Open Book Exam สำหรับ AI

RAG = 2 Phases

Phase A: Indexing (offline) — เตรียมข้อมูลล่วงหน้า ทำครั้งเดียวหรือ schedule

Phase B: Query (online) — ทุกครั้งที่ user ถาม

  1. Indexing PipelineDocuments → Cleaning → Chunking → Embedding → Vector DB
  2. Query PipelineQuestion → Embed → Vector Search → Re-rank → Context Assembly → LLM → Answer (with citations)

ทำไม RAG ถึงสำคัญที่สุด?

  • Solve Hallucination — LLM ตอบจากข้อมูลจริง ไม่เดา
  • Citation — บอกได้ว่าคำตอบมาจากเอกสารไหน → audit ได้
  • Knowledge Update — เพิ่มเอกสารใหม่ = bot อัปเดตทันที (ไม่ต้อง fine-tune)
  • Private Data — เอกสารบริษัทอยู่ใน vector DB ของคุณ ไม่หลุดไปเทรน LLM
  • ถูกกว่า Fine-tune 10-100× — ไม่ต้องใช้ GPU + dataset prep

Issues ที่ทุกคนเจอ (ทั้ง junior และ senior)

  • Bad Chunks — เล็กไป=ไม่มี context, ใหญ่ไป=noise เยอะ
  • Wrong Embedding Model — ใช้ English-only model กับเอกสารภาษาไทย → recall ตก
  • Retrieval Miss — เอกสารที่ถูกต้องไม่อยู่ใน top-K → LLM ไม่มีข้อมูล → แต่งหรือบอกไม่รู้
  • Hallucinated Citations — LLM อ้าง [source: 42] ทั้งที่ไม่มี source 42 อยู่
  • Outdated Index — เอกสารอัปเดตในระบบ แต่ vector DB ยังเป็นของเก่า
  • Multi-hop Question — "ใครคือ supplier ของ bearing ที่อยู่ใน P-101?" ต้องค้น 2 เอกสาร → 1 query หาไม่เจอ
  • Tables/Images Lost — text chunker ตัดตารางเป็นชิ้น ๆ → ความหมายหาย
  • Query-Document Mismatch — user เขียน "ปั๊มสั่น" doc เขียน "vibration anomaly" → embedding ใกล้กันไม่พอ

Resolutions แบบ Production

  • Smart Chunking → recursive splitter ตาม heading/sentence/paragraph + overlap 10-15% + เก็บ metadata
  • Hybrid Search → BM25 (keyword) + Dense (semantic) + RRF fusion — แก้ปัญหา query-doc mismatch ได้ดีมาก
  • Cross-Encoder Re-rank → Cohere Rerank / BGE-reranker → top-20 → top-3 ที่จริง ๆ relevant
  • Multilingual Embedding → BGE-M3, Cohere multilingual, OpenAI text-embedding-3 — สำหรับ Thai+English
  • Citation Enforcement → LLM ต้อง output {answer, sources: [id]} + validator เช็คว่า id มีจริง
  • Re-index Pipeline → schedule rebuild หรือ incremental update เมื่อ doc เปลี่ยน
  • Agentic RAG → multi-hop = LLM ทำ search → reason → search again loop
  • Tables/Images → extract เป็น structured data, embed description แยก, multimodal embedding
  • Query Rewriting → ก่อน search ให้ LLM rewrite query เป็นภาษาทางการ + synonyms (HyDE technique)

Strategy ที่ใช้งานจริง:

Setup Vector DB ใน 7 Steps

  1. Choose Embedding Modelกำหนด dimension (384/768/1536) — มีผลต่อ storage + speed
  2. Choose Vector DBดู scale + budget + ops capacity (ใช้ table ด้านบน)
  3. Define Schemavector + metadata (id, source, type, timestamp, tags) — metadata สำคัญพอ ๆ vector
  4. Configure IndexHNSW: M=16, ef_construction=200, ef_search=64 (good defaults)
  5. Bulk Insertbatch 100-1000 records, parallel workers, monitor memory
  6. Build Query APIvector + filter + top-K + optional re-rank — wrap เป็น service
  7. Monitor & Tunetrack recall, latency p95/p99, memory, cost/query

Code Example — pgvector + HNSW

-- Schema
CREATE EXTENSION vector;
CREATE TABLE doc_chunks (
  id BIGSERIAL PRIMARY KEY,
  source TEXT,
  equipment_type TEXT,
  page INT,
  content TEXT,
  embedding VECTOR(1536)
);

-- HNSW Index
CREATE INDEX ON doc_chunks
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 200);

-- Index metadata for filter
CREATE INDEX ON doc_chunks (equipment_type, page);

-- Query
SET hnsw.ef_search = 64;
SELECT id, content, source,
       1 - (embedding <=> $1::vector) AS score
FROM doc_chunks
WHERE equipment_type = $2
ORDER BY embedding <=> $1::vector
LIMIT 20;

Issues ที่ทำคน junior กระอัก

  • Cold Start — index 10M docs ใช้เวลา 6-12 ชม. (ไม่มีใครบอกล่วงหน้า)
  • Recall vs Latency — HNSW ef_search สูง = recall ดี แต่ช้า — ต้องเลือก
  • Embedding Model Lock-in — เปลี่ยน model = re-embed ทุก doc (เสียเวลา+เงินใหม่)
  • Metadata Filter Slow — filter ก่อน vector search → cardinality ผิด → query ช้า 100×
  • Storage Cost — 1M docs × 1536 dim × 4 bytes = 6 GB เฉพาะ vector (ยังไม่นับ index)
  • Hot/Cold Data — 20% ของ docs ถูก query 80% — แต่ทุกอันใช้ memory เท่ากัน
  • Multi-tenancy — ลูกค้าหลายราย แชร์ DB เดียว → data leak risk
  • Drift — เอกสารใหม่ใช้ embedding model ต่างจากเก่า → score ไม่เทียบกันได้

Resolutions แบบ Senior

  • Cold Start → batch + parallel workers (16+), checkpoint บ่อย, prioritize hot docs ก่อน
  • Recall vs Latency → A/B test ef_search 32/64/128 — เลือกจุดที่ recall ≥95% และ p95 <100ms
  • Embedding Lock-in → เก็บ raw text เสมอ, ใช้ versioned index, เปลี่ยน model ทำ blue-green deploy
  • Metadata Filter → index metadata column, ใช้ pre-filter เมื่อ selectivity สูง / post-filter เมื่อต่ำ
  • Storage → quantization (PQ/scalar) → ลด 4-32×, dimension reduction (Matryoshka embeddings)
  • Hot/Cold → tier storage: hot ใน RAM, cold ใน disk — Pinecone และ Qdrant รองรับ
  • Multi-tenancy → namespace per tenant, encryption at rest, RBAC
  • Drift → tag chunks ด้วย embedding_model_version, query ภายใน version เดียวกัน, plan migration
  • Semantic Cache → cache query → answer ใน Redis ด้วย similarity threshold (เซฟทั้ง LLM + vector calls)

Agent Loop Anatomy

def agent_loop(task, tools, max_iter=10, budget_usd=0.50):
    state = {"task": task, "history": []}
    cost = 0
    for step in range(max_iter):
        # 1. THINK: LLM decide next action
        thought = llm.complete(
            system="You have these tools: " + str(tools),
            user=f"Task: {task}\nHistory: {state['history']}\nWhat next?"
        )
        cost += thought.cost
        if cost > budget_usd:
            return "BUDGET_EXCEEDED"

        # 2. ACT: parse tool call
        if thought.is_done:
            return thought.final_answer
        tool_name, args = parse_tool_call(thought)

        # 3. OBSERVE: run tool, get result
        result = tools[tool_name](**args)
        state["history"].append({"step": step, "tool": tool_name, "result": result})

    return "MAX_ITERATIONS_REACHED"

@app.post("/diagnose")
async def diagnose(req: DiagnoseRequest):
    # 1. Cache check FIRST (sync, fast)
    cached = await cache.get(req.cache_key)
    if cached:
        return StreamingResponse(stream_cached(cached), media_type="text/event-stream")

    # 2. RAG retrieval
    context = await rag.retrieve(req.question)

    # 3. Stream LLM response
    async def event_stream():
        async for chunk in llm.stream(context=context, query=req.question):
            yield f"data: {json.dumps({'token': chunk.text})}\n\n"
        yield "data: [DONE]\n\n"

    return StreamingResponse(event_stream(), media_type="text/event-stream")

Production Issues ที่ทำให้คุณนอนไม่หลับ

  • Silent Failure — bot ตอบผิดเงียบ ๆ user ไม่รู้, คุณไม่เห็น
  • Cost Explosion — viral usage / loop / abuse → bill 10× ใน 1 วัน
  • Cache Invalidation Bug — เอกสารอัปเดต แต่ cache ยังเป็นของเก่า → ตอบผิด
  • 3rd-Party API Outage — OpenAI/Claude ล่ม 1 ชม. → ระบบคุณตามไป
  • Rate Limit Hit — เลี้ยง user เพิ่มขึ้น → API throttle → user error
  • Latency Spike — p99 พุ่งจาก 3s → 30s (cause: noisy neighbor / API region)
  • Memory Leak — vector DB / agent state ไม่ปล่อย → OOM
  • Prompt Injection in Production — user ใส่ adversarial → bot leak / ทำสิ่งไม่ควร
  • Drift — model หรือ data เปลี่ยน → quality ตกแบบไม่รู้ตัว
  • Compliance/Audit Failure — ลูกค้าขอ log การ access PII ไม่ได้
  • Vendor Lock-in — provider ขึ้นราคา 3× คุณย้ายไม่ได้เพราะออกแบบไม่เผื่อ
  • Knowledge Cutoff Confusion — user ถามเรื่องล่าสุด LLM ตอบจากข้อมูลเก่า

Senior's Production Survival Kit

  • Silent Failure → multi-signal monitoring (latency + cost + eval-in-prod + user 👍/👎) → alert บน drift ทันที
  • Cost Explosion → hard budget per user/org/day, rate limit per IP, anomaly detection บน $/min
  • Cache Invalidation → TTL + version tag + manual purge endpoint + smoke test ใน CI
  • 3rd-Party Outage → multi-provider fallback (Claude → GPT → Gemini), on-prem fallback model, degraded mode
  • Rate Limit → multiple API keys, rotate, queue, exponential backoff with jitter
  • Latency Spike → SLO-based alerting (p95/p99), distributed tracing, multi-region failover
  • Memory Leak → bounded queues, periodic restart, k8s memory limits + auto-restart
  • Prompt Injection → input sanitization, output validation, separate auth-context จาก user-content, prompt firewall (Lakera/Rebuff)
  • Drift → continuous eval (1-5% sampling) + canary monitoring + auto-rollback ถ้า quality ตก
  • Audit/Compliance → structured logs ทุก action, immutable storage, RBAC, GDPR-ready data retention
  • Vendor Lock-in → wrap provider ใน llm_client abstraction, test กับ ≥2 providers ตั้งแต่ day 1
  • Knowledge Cutoff → prefer RAG + web search tool over training knowledge, cite sources

🎯 Micro-Challenge

ออกแบบ system สำหรับ 1,000,000 requests/day — งบ <500k บาท/เดือน — p95 <3 sec

(คำนวณ: caching · model routing · infra cost · provider mix)

Math: 1M req/day = ~12 req/sec average, peak ~50/sec

  1. Caching attack: exact 30% + semantic 20% + prompt cache 50% of remaining input → effective LLM calls = ~40% = 400k/day
  2. Model routing: Haiku 70% (280k @ ~$0.0003) + Sonnet 25% (100k @ ~$0.003) + Opus 5% (20k @ ~$0.015) = ~$684/day = ~21k บาท/วัน = ~630k บาท/เดือน 😱
  3. Optimize เพิ่ม:
    • Prompt caching → ลด input tokens 70% → -25% cost
    • Increase semantic cache threshold + TTL → 20% → 30% hit rate
    • Quantization สำหรับ embedding → -50% storage
    • Redis cluster (self-host) แทน managed
  4. Final cost: ~400k บาท/เดือน LLM + 50k Redis + 30k vector DB + 20k monitoring = ~500k บาท/เดือน ✅
  5. Latency p95 <3s: cache hit ~50ms, miss with Haiku ~1.5s, Sonnet ~2.5s, Opus ~4s — average p95 ~2.8s ✅

Senior's truth: Caching + Routing = 80% ของ cost reduction. ถ้าคิด 2 อย่างนี้ก่อน → architecture ออกมาดีเอง
